# 执行摘要

无人机、无人车、无人船、移动机器人等无人装备正在经历一个共同变化：过去主要依赖远程操控和简单自动控制，现在逐步具备环境感知、定位导航、自主避障、目标识别乃至任务级理解与决策能力。随着这些能力增加，设备内部的计算节点已经不再只是“负责跑一个神经网络”的 AI 加速器，而越来越像一台受到体积、功耗、实时性和安全约束的小型异构计算机。

所谓**端侧智能计算**，是指将感知、定位、规划等计算直接部署在无人装备本机，而不是完全依赖远端服务器或云端。这样做的直接原因是无人装备常常存在网络不稳定、通信时延不可控、任务数据敏感以及必须本机完成安全闭环等问题。例如，一架无人机发现前方障碍物后，需要在很短时间内完成图像获取、障碍识别、距离判断、路径规划并把控制指令发送给飞控。如果整个链路依赖云端处理，即使云端模型速度很快，通信抖动也可能使系统失去实时性。

本次调研的核心判断是：**无人装备的“算力需求”不能简单等价为多少 TOPS。** TOPS（Tera Operations Per Second，万亿次运算每秒）通常用来描述 AI 加速器某种精度下的理论峰值运算能力，但一个无人系统同时还需要处理摄像头数据、图像预处理、视觉—惯性定位、地图构建、路径规划、网络通信和实时控制等任务。这些任务分别依赖中央处理器 CPU、图形处理器 GPU、神经网络处理器 NPU、图像信号处理器 ISP、视频编解码单元 VPU、内存带宽以及各种传感器接口。仅比较 TOPS，就像评价一台汽车只比较发动机峰值功率，而不考虑变速箱、制动、轮胎和底盘。

因此，本报告采用以下需求驱动路线：

```text
应用/任务场景
→ 功能栈
→ 工作负载
→ 数据量与实时性
→ CPU/GPU/NPU/内存/接口等系统资源
→ 计算架构
→ 芯片/模组/加速卡/整机
→ Benchmark 与工程验证
```

其中，**工作负载（Workload）**是连接“应用需要什么功能”和“硬件需要什么资源”的关键中间层。例如，“无人机自主避障”是一个应用能力，但在计算上会被拆解为摄像头采集、障碍感知、深度估计、局部地图、路径规划和飞控接口等多个 workload。只有把这些负载拆开，才能判断究竟是 NPU 不足、CPU 不足、内存带宽不足，还是摄像头接口和实时调度成为瓶颈。

针对无人装备的特殊使用环境，本报告进一步增加安全可信主线。这里所说的**安全可信**不仅是通信加密，而是从设备上电开始，一直到任务运行和后续升级，持续解决“这台设备是谁、它运行的软件是否被修改、AI 模型是否可信、密钥是否安全、远端能否确认设备当前状态”等问题。由此形成：

```text
任务需求 + 威胁模型
→ AI/实时工作负载 + 安全可信需求
→ 计算资源 + 安全资源
→ 计算架构 + Trust Plane
→ 平台 + 密码/可信根
→ 验证、升级与全生命周期管理
```

## 一、主要结论

### 1. 无人装备真正需要的是异构系统能力，而不是单一 AI 峰值算力

无人装备中的计算任务并不全部是神经网络推理。摄像头采集需要 ISP 和高速 I/O，视觉—惯性里程计需要 CPU/GPU 和精确时间同步，目标检测可能主要运行在 NPU，路径规划又可能主要消耗 CPU。多个任务同时运行时，还会共享内存和总线，因此系统的真实瓶颈往往出现在“资源竞争”和“数据搬运”，而不是某个计算单元的峰值算力。

基于已有场景、论文、官方平台和公开 Benchmark，本报告将端侧平台评价归纳为七类关键门槛：传感器与接口、实时分区、内存与带宽、计算引擎、并发与尾延迟、尺寸重量功耗与散热、软件与产品化。平台只有同时满足这些条件，才具有真正的系统适配能力。

### 2. 无人装备的智能程度不能简单用统一 L1–L5 表示

不同领域对“自主程度”的定义不同。道路车辆的 SAE J3016 关注驾驶自动化，无人船有 IMO MASS 体系，NIST ALFUS 则强调任务复杂度、环境复杂度和人类独立程度。把这些领域统一压缩成一个“越高级就需要越多 TOPS”的线性等级，会掩盖真实需求差异。

因此，本报告采用“任务场景 + 功能栈 + 自主性画像 + 工作负载画像”的方式描述无人系统。一个固定多摄像头监控设备可能没有自主导航，但视频计算量很大；一架轻型无人机可能计算量不高，却对闭环时延和重量极为敏感。二者不能简单放在同一等级轴比较。

### 3. 无人系统的计算任务可以归纳为九类工作负载

本报告将常见任务归纳为 W1–W9。它们并不是“能力等级”，而是便于资源预算和平台选型的负载分类：

- W1：传感器输入与视频流水线；
- W2：状态估计与定位；
- W3：深度神经网络感知；
- W4：三维地图与世界表示；
- W5：跟踪、预测与态势理解；
- W6：规划、优化与决策；
- W7：大模型、视觉语言模型和视觉语言动作模型；
- W8：多机协同和集群计算；
- W9：安全监督与实时控制相关任务。

真正的无人系统通常是多个 workload 同时运行，而不是只运行其中一个。

### 4. 多摄像头平台首先是数据系统，其次才是 AI 系统

六个摄像头接入一台计算平台后，不一定六路全部进入目标检测，也不一定六路都进入 SLAM。不同摄像头可能承担不同任务：部分用于定位，部分用于障碍检测，部分只录像，某些多视图算法还可能一次把多路图像一起输入一个融合模型。

因此，本报告引入 Camera Routing Set，将物理采集、VIO、独立检测、多视图融合、深度和录像分别记录。这样才能计算真实的数据流和模型调用率，避免简单把“摄像头数量 × 单路模型 FPS”作为总需求。

### 5. 实时性必须从完整闭环判断，而不是只看模型推理时间

在无人机避障场景中，真正有意义的是“从环境变化发生，到飞行器开始执行规避动作”需要多长时间。图像可能要等待下一帧，随后经过 ISP、排队、感知、建图、规划，再通过飞控输出，最终机体还需要一定时间改变运动状态。

因此，即便神经网络本身只运行 20 ms，如果排队、图像搬运和规划又增加 100 ms，最终仍可能无法满足高速飞行的避障要求。报告因此重点关注 P95/P99 尾延迟、Frame Age（帧龄，即当前计算结果所对应图像已经“老了多久”）和 deadline miss（截止时间违约），而不是只比较平均 FPS。

### 6. 端侧计算产品已经形成多种形态，不能混为一类

目前市场上既有高集成 SoC/SoM，也有 GPU 机器人计算机、独立 M.2/PCIe AI 加速卡、工业边缘计算机以及 Host+Accelerator 异构算力盒。它们解决的问题并不相同。

例如，一张 M.2 AI 加速卡可以非常擅长目标检测，但它通常不负责摄像头 ISP、VIO、系统调度和路径规划；而高集成 SoC 虽然 AI 峰值算力可能较低，却可以在一个芯片内完成摄像头接入、视频处理、CPU 计算和 NPU 推理。因此产品比较必须首先按形态分类，再谈具体适配场景。

### 7. 更有差异化价值的方向是“安全可信无人智能计算平台”

通用 AI Box 市场已经存在较多成熟产品。如果仅以“更高 TOPS、更小尺寸、更多接口”为目标，产品容易陷入同质化竞争。

结合公司已有密码安全和可信计算技术积累，更值得形成的产品定位是：

> **智能计算 + 实时控制协同 + 密码安全 + 平台可信。**

平台可以划分为三个相互协同的逻辑平面：计算平面（Compute Plane）、实时控制平面（Real-Time Plane）和可信平面（Trust Plane）。其中 Trust Plane 不只是增加一个密码芯片，而是贯穿设备身份、启动完整性、密钥、AI 模型可信、通信安全、远程证明、安全升级和物理失陷处置。

### 8. 六摄像头无人平台是非常合适的方法验证 Case

现有项目已经确认六路摄像头采集需求，并逐步向同步采集、目标检测、多摄融合、深度、VIO/SLAM、避障和自主导航演进。该项目正好可以把“应用需求—工作负载—资源预算—架构选择—Benchmark”这套方法完整跑通。

但目前实际 FPS、六路工作模式、检测路数、VIO 路数、飞行速度和有效探测距离等参数尚未全部冻结。因此，现阶段最专业的做法不是先给出一个“需要 50 TOPS 或 100 TOPS”的数字，而是保留这些变量，通过后续工程测试逐步收敛。

# 第一章 调研背景与研究方法

## 1.1 调研背景

传统无人装备的机载计算通常可以分为两部分：一部分是飞行控制或运动控制，负责姿态、速度、航向等低层闭环；另一部分是任务载荷，例如摄像、图传和简单数据处理。这类系统的计算资源相对固定，主要关注实时性和可靠性。

随着人工智能进入无人平台，系统开始增加目标检测、障碍识别、视觉定位、地图构建和自主规划等能力。一个典型的视觉自主无人机，不仅需要“看见”前方物体，还要判断自身如何运动、障碍物与自己的相对位置、未来轨迹是否会发生碰撞，以及应当选择什么规避路径。这样一来，计算节点就需要同时运行传统控制算法、计算机视觉算法和深度学习模型。

进一步发展到视觉语言模型（Vision-Language Model，VLM）和视觉语言动作模型（Vision-Language-Action，VLA）之后，端侧平台还可能承担场景语义理解、自然语言任务输入和高层任务规划。这种演进使端侧计算逐渐从“一个模型对应一块加速器”变成“多个不同性质的任务共用一套异构计算系统”。

因此，本报告的研究重点不是列举市场上的算力卡，而是回答：**面向无人装备的具体任务，系统到底需要哪些计算能力，为什么需要，以及现有平台能否以可接受的功耗、尺寸、实时性和安全性实现。**

## 1.2 研究对象

本调研覆盖以下六类场景：

1. 无人机（UAV/UAS）；
2. 无人车和自动驾驶平台（UGV）；
3. 无人船（USV）；
4. 自主移动机器人（AMR）和其他移动机器人；
5. 操作机器人和具身智能；
6. 固定式多摄像头边缘智能设备及多无人系统。

其中六摄像头无人机是本项目当前最具体的工程案例，但它只用于验证方法，不作为全行业需求的唯一来源。

## 1.3 研究方法：从任务出发，而不是从芯片出发

本报告采用如下分析链：

```text
Mission
→ Sensor / Function
→ Workload
→ Resource Budget
→ Latency Budget
→ Architecture Gate
→ Candidate Platform
→ Validation
```

Mission 指任务本身，例如“GNSS 拒止条件下自主巡检”；Sensor/Function 指为完成任务必须具备哪些传感器和功能；Workload 将功能进一步翻译成实际计算任务；Resource Budget 则估算 CPU、GPU、NPU、内存、接口和功耗等资源。

所谓 Architecture Gate，可以理解为“架构门槛”。它不是给平台打分，而是逐项回答“这个平台能不能过关”。例如，如果目标系统需要六路同步摄像头，而候选平台在物理接口层无法实现，那么无论其 AI TOPS 多高，都应首先判定存在硬约束。

## 1.4 Requirement Vector：把需求写成可计算参数

为了避免需求只停留在“需要自主避障”“需要大模型”这类模糊描述，本报告建议对每个目标系统建立 Requirement Vector（需求向量）：

```text
R = {
  Mission,
  Sensors,
  DataRate,
  Synchronization,
  WorkloadSet,
  Concurrency,
  UpdateRate,
  Deadline,
  Memory,
  I/O,
  SWaP-C,
  Safety,
  Security,
  Software,
  Productization
}
```

其中 SWaP-C 是 Size、Weight、Power and Cost 的缩写，即尺寸、重量、功耗和成本。这一指标在无人机上尤为关键，因为计算能力提升往往会带来更大散热器、更高电源功耗和更短续航。

## 1.5 证据分级

为避免把厂商宣传资料直接当成工程事实，本报告将证据分为以下类型：

- FACT：由标准、官方文档或可靠资料确认的事实；
- CASE：已经存在的真实产品或系统案例；
- BENCH：测试条件明确的 Benchmark；
- PAPER：论文或高质量综述；
- SPEC：官方规格和开发资料；
- VENDOR：厂商自述但未被独立验证的能力；
- INFER：依据已知事实形成的工程推断；
- GAP：当前缺乏足够资料或项目参数尚未冻结。

当不同平台缺少统一模型、统一输入尺寸、统一软件版本和统一功耗条件时，本报告不会做强行性能排序。

## 1.6 为什么不能把 TOPS 当成“算力需求”

TOPS 的全称是 Tera Operations Per Second，表示每秒万亿次运算。AI 芯片厂商常以 INT8、INT4 等低精度整数计算下的 TOPS 作为峰值指标。

问题在于，峰值 TOPS 与实际无人系统性能之间还隔着很多环节。首先，模型是否支持目标 NPU 的算子和编译器，会决定峰值算力能否真正利用；其次，图像需要先经过 ISP、缩放和格式转换，数据还要从摄像头搬到内存，再送入 NPU；再次，VIO、SLAM 和规划并不一定适合 NPU，它们可能主要依赖 CPU 或 GPU。

因此，一个 160 TOPS 的独立加速器，如果依赖的 Host 很弱，系统仍可能在图像输入、PCIe 数据搬运、VIO 或规划阶段产生瓶颈。相反，一个 20 TOPS 的高度集成 SoC，在某些多摄像头实时系统中可能更容易形成稳定的数据闭环。

# 第二章 专业术语与缩略语说明

本章用于集中解释报告中反复出现的专业术语。正文中关键术语第一次出现时仍会给出中文解释，本章便于读者后续快速查阅。

## 2.1 计算与硬件术语

| 缩写/术语 | 中文 | 含义及与无人装备的关系 |
|---|---|---|
| CPU | 中央处理器 | 负责操作系统、驱动、调度、规划、图优化等通用计算。无人系统中大量非神经网络任务仍主要依赖 CPU。 |
| GPU | 图形处理器/通用并行处理器 | 原本用于图形计算，现广泛用于深度学习、视觉、点云、VIO 和 Transformer。通用性通常高于专用 NPU。 |
| NPU | 神经网络处理器 | 专门加速卷积、矩阵乘等 AI 运算，通常能效较高，但模型支持程度依赖厂商编译器和算子覆盖。 |
| AI ASIC | AI 专用集成电路 | 为 AI 工作负载专门设计的芯片，可表现为独立加速卡或 SoC 内部计算单元。 |
| MCU | 微控制器 | 适合确定性控制、传感器管理和实时任务，常用于飞控或安全监督。 |
| SoC | 片上系统 | 将 CPU、GPU/NPU、ISP、接口等集成到单颗芯片中。 |
| SoM | 系统级模块/核心板 | 将 SoC、内存和关键电源等做成可直接集成的模块，方便产品开发。 |
| TOPS | 每秒万亿次运算 | AI 芯片理论峰值指标之一，必须同时注明精度，如 INT8 TOPS。不能代表完整系统性能。 |
| FLOPS | 每秒浮点运算次数 | 常用于 FP16/BF16/FP32 等浮点计算性能描述。 |
| DDR/LPDDR | 双倍速率内存/低功耗内存 | 系统运行内存及共享数据通路。多摄像头、SLAM、大模型都可能受内存容量和带宽限制。 |
| ISP | 图像信号处理器 | 负责 RAW 图像处理、去噪、白平衡、HDR、颜色转换等。多摄像头系统的重要资源。 |
| VPU | 视频处理单元 | 负责 H.264/H.265 等硬件编码和解码，可显著降低 CPU 占用。 |
| DMA | 直接存储器访问 | 允许外设与内存之间直接搬运数据，减少 CPU 参与和拷贝。 |
| Zero-copy | 零拷贝 | 尽量让多个处理模块共享同一块数据缓冲区，减少图像反复复制，降低 DDR 压力和延迟。 |
| PCIe | 高速串行扩展总线 | Host 与 M.2/PCIe AI 加速卡之间常用的高速接口。 |
| MIPI CSI | 移动产业处理器接口-摄像头串行接口 | SoC 直接接摄像头常用接口。 |
| GMSL / FPD-Link | 汽车高速摄像头串行链路 | 适合较长距离、多路摄像头和抗干扰传输，机器人/车辆常用。 |
| SWaP-C | 尺寸、重量、功耗、成本 | 无人装备平台选型的重要系统约束。 |

## 2.2 机器人与自主系统术语

| 缩写/术语 | 中文 | 含义 |
|---|---|---|
| UAV/UAS | 无人机/无人航空系统 | 低空无人平台及其完整系统。 |
| UGV | 无人地面车辆 | 包括自动驾驶车辆、园区车和特种无人车。 |

# 第三章 无人装备智能化应用与计算任务

## 3.1 通用自主系统功能栈

不同无人装备外形和任务差异很大，但其自主系统通常遵循相似的信息处理链：先获取环境和自身状态数据，然后估计当前位置，识别周围物体和环境，构建地图或世界表示，再进行预测和规划，最后形成控制指令。

可以抽象为：

```text
F1 传感器采集
→ F2 状态估计与定位
→ F3 地图/世界建模
→ F4 环境感知
→ F5 预测与态势理解
→ F6 规划与决策
→ F7 控制与执行
```

除此之外还存在任务管理、人机交互、多机协同以及安全健康管理等横向功能。

这个功能栈的重要意义在于，它让我们能够从“无人机”“无人车”这些产品名称中抽离出来，看到背后真正消耗计算资源的任务。例如无人机和 AMR 都可能需要 VIO 和局部路径规划，因此它们在某些 workload 上具有共性；而固定多摄像头系统虽然没有飞行控制，却可能拥有更大的视频吞吐量。

## 3.2 无人机 UAV/UAS

无人机的典型应用包括巡检、测绘、监视、搜索救援、物流运输和复杂环境自主飞行。早期无人机主要依赖 GNSS/INS 和飞控完成航迹跟踪，摄像头更多是任务载荷。随着自主性提高，摄像头逐步参与飞行本身。

例如在 GNSS 拒止场景中，全球导航卫星系统不可用，无人机需要利用视觉—惯性里程计（VIO）或同时定位与建图（SLAM）估计自身位置。此时摄像头和 IMU 不再只是“采集数据”，而是进入核心导航链路。如果无人机还需要自主避障，则又要叠加目标/障碍感知、局部地图和路径规划。

这类平台最突出的工程矛盾是 SWaP-C。无人机对重量和功耗非常敏感，计算性能提升可能直接缩短续航；同时机体振动、快速运动和多摄像头同步又提高了算法难度。因此无人机计算平台不能简单照搬地面服务器或机器人整机。

## 3.3 无人车 UGV 与自动驾驶

UGV 和自动驾驶平台通常拥有更高功耗预算，也允许使用更大的散热系统，因此可部署更多传感器和更强计算平台。典型系统会同时使用 Camera、LiDAR、Radar、GNSS/IMU，并运行定位、目标感知、轨迹预测、行为规划和车辆控制。

自动驾驶近年来大量采用 BEV（Bird's-Eye View，鸟瞰视角表示）和 Occupancy（占据表示）。其核心思想是把多个摄像头或多种传感器的结果映射到统一的三维或俯视坐标中，使系统能够回答“周围空间哪里被占据、哪里可以行驶”。这种算法相比单摄像头目标检测更依赖多视图融合、Transformer 和大内存带宽。

因此，自动驾驶类平台通常代表端侧异构计算的高端形态：不只是 NPU 大，而是 CPU、GPU、NPU、实时控制、传感器接口和安全机制都相对完整。

## 3.4 自主移动机器人 AMR

AMR（Autonomous Mobile Robot，自主移动机器人）常用于仓储、制造物流、巡检和服务场景。它的核心问题是“我在哪里、周围有什么、我要到哪里去”。

与无人机相比，AMR 速度通常较低、工作环境更结构化，因此对重量的敏感度相对较低，但更强调长期连续运行、人机混行、地图变化以及多机器人调度。很多 AMR 会使用 2D/3D LiDAR、Camera、轮速计和 IMU，同时运行 SLAM、代价地图、全局路径规划和局部避障。

从算力角度看，AMR 是研究 CPU/GPU/NPU 协同的典型场景，因为其规划和地图任务往往长期占用 CPU，而视觉/深度学习任务则更依赖 GPU/NPU。

## 3.5 无人船 USV

USV（Unmanned Surface Vehicle，无人水面艇）工作在海洋或内河环境。除了视觉之外，它通常还会使用 Radar、AIS、GNSS 和惯性导航等信息。

海面环境有几个特殊问题：水面反光和天气变化会影响视觉；目标运动范围大；船只之间还要遵循 COLREGs 等航行规则。因此 USV 的核心计算往往不是单纯目标检测，而是多传感器融合、目标跟踪、碰撞风险预测和规则约束下的路径规划。

USV 的续航时间通常比小型无人机长，允许更高计算功耗，但对可靠性、通信覆盖和长期稳定运行要求更高。

## 3.6 操作机器人与具身智能

操作机器人除了“移动到目标位置”，还需要完成抓取、装配、操作工具等任务。传统方案依赖目标识别、姿态估计、运动规划和力控制。

近年来视觉语言模型（VLM）和视觉语言动作模型（VLA）开始进入机器人领域。VLM 能够回答“画面中有什么、当前任务应该怎么理解”，VLA 则进一步尝试直接输出动作或动作序列。

这类模型提高了机器人处理开放环境和自然语言任务的潜力，但同时大幅增加内存和算力需求。更重要的是，大模型产生的动作并不天然满足实时性和安全约束，因此当前更合理的工程路径仍是让大模型承担任务理解和高层规划，底层避障、控制和安全监督仍由确定性模块负责。

## 3.7 固定式边缘智能

固定式边缘智能设备虽然不会移动，但常常同时接入大量摄像头。例如工业视觉、交通分析和安防系统可能需要处理 8 路、16 路甚至更多视频。

这种场景说明一个重要问题：自主性和算力不是同一个维度。固定式设备不需要 SLAM 和规划，但视频解码、目标检测和多路跟踪可能非常重。因此平台选型首先看视频吞吐、NPU 并发和内存带宽，而不是是否具备实时控制器。

## 3.8 自主性画像

为避免简单使用统一 L1–L5，本报告使用三个维度描述自主程度：

- Mission Complexity：任务复杂度，例如固定航线巡检还是开放环境多步骤任务；
- Environmental Complexity：环境复杂度，例如结构化仓库还是 GNSS 拒止、动态低空环境；
- Human Independence：人类独立程度，例如持续遥控、人工监督还是仅给出目标后自主执行。

这种描述能够更真实地解释为什么两个“看起来都很智能”的系统会有完全不同的算力需求。

# 第四章 典型工作负载与组合模型

## 4.1 为什么要建立 W1–W9

“目标检测”“SLAM”“路径规划”在算法层完全不同，如果只用一个总 TOPS 表示，会丢失最关键的硬件差异。因此本报告将自主系统拆成九类工作负载。

W1–W9 的目的不是重新发明一套智能等级，而是让工程师能够回答：这个系统到底有多少图像流、多少定位计算、多少 DNN 推理、多少规划任务，以及它们是否同时运行。

## 4.2 W1：传感器输入与视频流水线

W1 包括摄像头采集、ISP、格式转换、视频编码、时间戳和 DMA 等任务。它在系统中处于最前端，相当于所有视觉算法的数据入口。

很多平台宣传重点放在 AI TOPS，但如果摄像头根本无法按目标路数和帧率稳定接入，或者图像在 ISP、内存和预处理阶段出现掉帧，后面的 NPU 再强也没有意义。

W1 的核心指标包括像素率、视频编码通道数、帧丢失、时间戳抖动和内存拷贝次数。对于多摄像头无人机，W1 往往是第一个需要验证的 Gate。

## 4.3 W2：状态估计与定位

W2 用于回答“设备现在在哪里、怎么运动”。典型算法包括 GNSS/INS 融合、光流、视觉里程计 VO、视觉—惯性里程计 VIO，以及激光/视觉地图匹配。

VIO 的基本思路是把摄像头看到的特征运动和 IMU 测到的加速度、角速度结合起来，互相校正，从而得到更稳定的位置和姿态估计。这类算法包含特征提取、匹配、非线性优化和状态估计，往往大量使用 CPU，也可能使用 GPU，但通常不能简单搬到 NPU 上执行。

因此，如果一个平台 NPU 很强但 CPU 很弱，它可能适合视频分析，却未必适合视觉自主导航。

## 4.4 W3：深度神经网络感知

W3 是最接近传统“AI 算力”概念的部分，包括目标检测、分类、语义分割、深度估计、姿态识别和可通行区域识别等。

这类任务通常适合 NPU 或 GPU。平台实际表现不仅取决于 TOPS，还取决于模型是否能够成功转换、算子是否完整支持、输入尺寸是否合适、预处理和后处理是否高效，以及多个模型同时运行时资源是否争抢。

例如同样是 20 TOPS，不同 NPU 对 Transformer、动态 shape 或特殊算子的支持可能完全不同，因此“模型能不能跑”和“峰值算力是多少”是两个问题。

## 4.5 W4：地图与世界表示

W4 用于形成环境的内部表示。传统机器人常使用二维栅格地图、点云地图和 SLAM 地图；更高级系统则使用 BEV、Occupancy 或语义地图。

地图任务通常需要长期保存和更新空间状态，因此对内存容量和带宽影响很大。随着地图范围扩大，内存占用还可能持续增长。对自动驾驶和多传感器系统而言，W4 往往同时调用 CPU、GPU 和大量 DDR。

## 4.6 W5：跟踪、预测和态势理解

目标检测只回答“这一帧里有什么”，而跟踪和预测要回答“这个对象是谁、它往哪里走、下一步可能发生什么”。

多目标跟踪需要维护历史状态；轨迹预测需要利用一段时间的运动信息；复杂场景理解还可能使用 Transformer 或 VLM。由此带来的主要变化是系统开始需要时序信息，而不仅是逐帧推理。

## 4.7 W6：规划、优化与决策

W6 负责把“环境理解”转化成“下一步怎么走”。A*、Dijkstra、RRT 等算法用于搜索路径，MPC（Model Predictive Control，模型预测控制）则通过动态模型预测未来状态并求解最优控制量。

规划任务常有明显的最坏情况延迟问题：简单场景可能很快，但复杂障碍场景搜索空间增大时，耗时可能突然上升。因此评估 W6 时不能只看平均速度，需要关注 P95/P99 和 Worst-Case Latency。

## 4.8 W7：基础模型、VLM、LLM 与 VLA

W7 代表当前最受关注的大模型方向。LLM 是大语言模型，VLM 在语言之外加入视觉理解，VLA 则进一步将视觉和语言输入映射到动作。

对端侧平台而言，W7 的主要挑战常常不是传统 INT8 TOPS，而是内存容量和带宽。大模型权重本身就可能占用数 GB 到数十 GB，推理还需要 Activation、Workspace 和 KV Cache。

因此，当平台开始支持 VLM/VLA 时，16GB、32GB、64GB 甚至更大的内存，以及 INT4/FP8/FP16 等多精度能力会越来越重要。但 W7 应被视为对现有自主系统的增量能力，而不是直接替代 W2/W3/W6 的安全闭环。

## 4.9 W8：多机协同与集群计算

W8 面向多无人机、多机器人或 Fleet 场景。系统除本机计算外，还需要交换位置、任务、地图或感知结果。

此时网络延迟、带宽、QoS、设备身份和分布式一致性都会成为系统资源。对于大规模编队，单机算力并不是唯一问题，通信和协同算法可能反而决定系统上限。

## 4.10 W9：安全监督与控制

W9 包括飞控、运动控制、安全监督、故障检测和应急降级等任务。

这类任务的特点是“算得不一定多，但必须按时算完”。例如 400 Hz 飞控循环并不需要几十 TOPS，但如果调度偶尔阻塞几十毫秒，后果可能比目标检测慢一帧严重得多。

因此，W9 的核心是确定性和故障隔离，而不是 AI 吞吐。

## 4.11 典型 Workload Composition

为了描述现实系统，本报告进一步用 C1–C5 表示常见 workload 组合。

### C1 多摄像头智能分析

```text
W1 + W3 + W5
(+ W7 按需)
```

典型是固定边缘视觉节点。它没有定位和控制，因此适合高度优化的视频 SoC 或 Host+Accelerator。

### C2 视觉自主系统

```text
W1 + W2 + W3 + W4 + W6 + W9
```

典型是视觉自主无人机和 AMR。相比 C1，最大变化是加入定位、地图、规划和闭环，因此 CPU、同步和尾延迟重要性显著提高。

### C3 多传感器自主系统

```text
W1 + W2 + W3 + W4 + W5 + W6 + W9
```

典型是自动驾驶和 Radar/Camera/LiDAR 融合系统，要求更高的接口数量、内存容量和异构计算能力。

### C4 大模型增强机器人

```text
基础自主系统 + W7
```

VLM/VLA 更多承担语义理解、高层决策和任务交互。

### C5 协同自主系统

在 C2/C3 等单机能力基础上叠加 W8，用于 Fleet 和多无人平台协同。

# 第五章 从工作负载推导端侧系统资源

## 5.1 先算数据，再算 AI

多摄像头系统首先要回答“每秒到底有多少数据进入系统”。如果有 N 路摄像头，每路分辨率为 W×H、帧率为 FPS，则像素率可以近似表示为：

```text
PixelRate = Σ(N × W × H × FPS)
```

但像素率只是第一步。RAW 图像、NV12 图像和 RGB 图像每像素占用字节数不同；经过 ISP 后还可能产生多个分辨率的输出；录像、AI 和 VIO 又可能同时读取同一帧。

因此真实 DDR 工作流量往往明显大于“一份图像数据量”。工程上需要继续追踪每一帧经过多少次读写和复制。

## 5.2 Camera Routing：摄像头不等于算法路数

对多摄系统，本报告使用：

```text
C = 物理采集路数
V = 进入 VIO/SLAM 的摄像头集合
P = 独立逐路感知集合
F = 多视图融合集合
D = 深度/双目集合
R = 录像集合
```

例如六摄无人机可以六路全部采集，但可能只有前视和下视进入 VIO，四路进入障碍检测，六路都录像。也可能采用多视图融合模型，一次调用同时读取四路图像。

这种区分会直接改变 NPU 调用次数和内存访问量，因此是多摄系统资源预算的基础。

## 5.3 PER_VIEW 与 FUSED_MULTI_VIEW

PER_VIEW 表示每个视角独立运行一个模型。例如四路摄像头各以 15 Hz 做目标检测，则总模型调用率约为 60 次/秒。

FUSED_MULTI_VIEW 表示一个模型调用同时使用多个视角。例如四路摄像头一起输入 BEV 网络，每秒更新 10 次，那么模型调用率只是 10 次/秒，但输入视图率仍是 40 view/s，而且模型本身通常更复杂、内存更大。

这也是为什么不能简单用“摄像头数 × 单路模型 FPS”估算所有多摄系统。

## 5.4 CPU 需求

CPU 在无人平台中负责大量“胶水”和算法工作，包括驱动、ROS 2 节点、VIO 图优化、跟踪后处理、路径规划、网络和存储。

尤其在 C2 Visual Autonomy 中，CPU 往往不是辅助资源，而是核心资源。平台评估时应关注多线程性能、调度行为、实时优先级和 P95/P99 延迟，而不是只看 CPU 核数。

## 5.5 GPU 需求

GPU 兼具高并行性和通用性，可以运行 CUDA/OpenCL 算法、VIO、点云、深度估计、BEV、Transformer 和大模型。

相比专用 NPU，GPU 通常软件生态更成熟、灵活性更高，但单位功耗下能效可能较低。对于同时运行传统视觉和新型 Transformer 的机器人，GPU 的价值往往不只是 AI 推理，而是“多种 workload 共用一套通用并行引擎”。

## 5.6 NPU / AI ASIC 需求

NPU 或 AI ASIC 最适合规则较明确的大规模张量运算。目标检测、分割和量化 Transformer 都可能获得很高能效。

但选择 NPU 时需要重点检查：

- 目标模型算子能否完整支持；
- 是否需要替换或改写算子；
- 支持 INT8、INT4、FP16 等哪些精度；
- 是否支持多个并发模型；
- 动态 shape 是否可用；
- Host 与 NPU 之间如何共享数据；
- 编译和调试工具是否成熟。

这些因素决定的是真实工程成本，而不是 datasheet 上的峰值数字。

## 5.7 内存容量

内存不仅放模型权重，还要同时容纳操作系统、摄像头缓冲、VIO 状态、地图、运行时 workspace 和各种队列。

当加入 VLM/LLM 后，还要增加 KV Cache。一个 7B 模型即使做 INT4 量化，权重也仍然占用数 GB，因此“能否把模型装进内存”会先于 TOPS 成为硬约束。

## 5.8 DDR 带宽

CPU、GPU、NPU、ISP 和 VPU 可能共同访问同一 LPDDR。多路图像、大模型和 SLAM 同时运行时，理论内存峰值带宽并不能全部提供给某个任务。

因此系统需要评估稳态带宽、突发访问、拷贝次数和 zero-copy 覆盖。实际工程中，减少一次全帧复制有时比增加若干 TOPS 更有效。

## 5.9 ISP / VPU

ISP（Image Signal Processor，图像信号处理器）负责把传感器输出的 RAW 数据变成算法可用图像。VPU（Video Processing Unit，视频处理单元）负责视频编码和解码。

多摄像头平台如果缺少足够 ISP pipeline，可能需要外部 ISP 或降低路数；如果录像依赖 CPU 软件编码，也会大量侵占资源。因此 ISP/VPU 应作为平台一级指标，而不是附件规格。

## 5.10 I/O 与传感器接口

MIPI CSI 常用于板内短距离摄像头连接；GMSL/FPD-Link 更适合车载和机器人长线缆连接；PCIe 常用于连接高速 AI accelerator；CAN/CAN-FD 则常用于控制器和车载设备。

平台页面写有“多个接口”并不等于都能同时满带宽使用。还需确认 lane 数量、共享总线、PHY、SerDes、交换芯片和硬件同步机制。

## 5.11 闭环时延

自主避障的总响应时间可以表示为：

```text
T_reaction =
T_sample
+ T_sensor/ISP
+ T_queue
+ T_perception
+ T_fusion/map
+ T_planner
+ T_command
+ T_vehicle_response
```

例如无人机以 10 m/s 飞行，如果完整反应时间为 200 ms，那么在这段时间内机体已经前进约 2 m。由此可以看出，时延只有结合飞行速度、探测距离和制动/转向能力才有意义。

因此平台选型不能问“YOLO 是 50 FPS 还是 100 FPS”，而应问：“在所有 workload 并发、热稳态条件下，感知到控制的 P99 Frame Age 是否仍满足任务闭环？”

## 5.12 并发和尾延迟

如果同一 NPU 需要同时运行目标检测和深度网络，同一 GPU 又承担 VIO 和地图，平均性能可能很好，但某些时刻会因为资源抢占产生长尾。

P95/P99 用于描述这种尾延迟。例如 P99=100 ms 表示 99%的请求能在 100 ms 内完成，但仍有 1%更慢。对安全关键任务来说，这 1%可能决定系统能否稳定运行。

# 第六章 端侧计算技术路线

## 6.1 高集成异构 SoC / SoM

SoC（System on Chip，片上系统）将 CPU、GPU/NPU、ISP、视频和接口集成在单颗芯片中；SoM（System on Module）则进一步把 SoC、内存和关键电路做成可直接集成的核心模块。

这种路线的主要优势是数据链短。摄像头进入 ISP 后可以直接使用共享内存，再由 NPU/GPU 处理，不需要跨 PCIe 搬运大块图像。对无人机这类 SWaP-C 敏感设备，这种高集成方案通常更有吸引力。

缺点是平台能力与厂商软件栈绑定较深。一旦 NPU 算子覆盖不足、ROS 支持较弱或者安全机制不完整，产品迁移成本可能很高。

## 6.2 GPU 边缘计算机

以 NVIDIA Jetson 为代表的 GPU Edge Computer 更接近一台小型通用并行计算机。GPU 不仅能运行 DNN，还能执行 CUDA 视觉算法、VSLAM、点云和 Transformer。

这种路线特别适合算法快速迭代和多 workload 混合，因为开发者可以在相对统一的软件生态中完成不同任务。

问题是 GPU 平台一般功耗和散热压力较大。在小型 UAV 上，散热器、载板和电源会显著增加重量，因此必须看整机，而不能只看核心模块。

## 6.3 NPU / AI ASIC

专用 NPU 或 AI ASIC 追求单位功耗下更高的神经网络吞吐。Hailo、Axelera、后摩等独立 accelerator 属于这一类。

这类产品很适合把 W3 DNN 感知从 Host 卸载出来，使 Host 保留更多 CPU/GPU 资源给 VIO 和规划。但 accelerator 自身通常不具备完整机器人系统能力，所以不能脱离 Host 单独评价。

## 6.4 Host + Accelerator

Host+Accelerator 是目前值得重点关注的异构路线。Host 可能是 RK3588、x86 或其他 ARM SoC，负责摄像头、系统调度、VIO 和规划；M.2/PCIe 加速卡负责目标检测或大模型。

这种架构的优势是模块化：同一 Host 可以换不同 accelerator，形成多个产品档位。缺点是数据需要经过 PCIe，增加 H2D（Host to Device，主机到加速器）和 D2H（Device to Host，加速器回主机）的搬运。

因此评价“160 TOPS M.2 卡”时，必须同时回答 Host 的 CPU、DDR、摄像头和 PCIe 是否足够，否则这个 TOPS 没有完整系统意义。

## 6.5 实时控制器 + 伴随计算机

无人机和机器人常采用 FCU/MCU + Companion Computer 的分层结构。

FCU（Flight Control Unit，飞行控制单元）或 MCU 负责姿态控制、执行机构和 failsafe；伴随计算机负责视觉、AI、SLAM 和规划。

这种架构的最大价值是隔离：Linux 和 AI workload 即使偶尔发生调度抖动，也不直接破坏高频硬实时控制。对于安全可信平台，还可以进一步把两个计算域之间的通信纳入身份认证和权限控制。

## 6.6 Edge Server 与 Edge-Cloud

更大规模的无人系统可能把部分计算卸载到近端边缘服务器或云端，例如全局地图融合、多机任务分配和大模型推理。

但安全关键闭环不能假定网络永远存在，因此系统必须设计降级模式：断网后仍应保留基本定位、避障和安全返航能力。

# 第七章 主流端侧计算产品与解决方案现状

## 7.1 为什么先分产品形态

市场上的“算力产品”实际上可能是芯片、SoM、开发板、M.2 卡、机器人整机或服务器。如果把它们都放在同一张 TOPS 表里，就会产生大量误导。

例如开发板的接口和散热并不等于量产产品，M.2 卡也不包含 Host，而工业机器人计算机虽然体积较大，却可能已经集成 GMSL、CAN、宽压电源和工业温度设计。

因此本报告首先按产品形态分类，再讨论其适合承担的 workload。

## 7.2 高集成 SoM / Robotics Platform

这一类代表包括 NVIDIA Jetson Orin、Qualcomm Dragonwing IQ-9075、RK3588、Atlas 200I A2、BM1688 等。

它们共同特点是把 CPU、AI 加速和多媒体能力集中在同一平台。对于 C2 Visual Autonomy，优势在于 W1/W2/W3/W4/W6 可以在较短数据路径中协同。

NVIDIA Jetson 的突出特点是 CUDA、TensorRT 和 Isaac ROS 生态完整，因此公开的机器人、多摄像头、VSLAM 和深度感知案例较多。其不足主要是成本、功耗和国产化。

RK3588 的优势是成本和国内生态，同时拥有 NPU、ISP 和视频能力，适合作为低成本 integrated host。但其是否能满足“六路摄像头 + VIO + DNN + Planner”不能从 6 TOPS 这一规格直接得出，需要实际 Camera/DDR/并发 Benchmark。

Qualcomm IQ-9075 更强调机器人和多摄像头异构架构，并具有实时子系统等能力。从产品定位上看，它代表“机器人专用 SoC”路线，但具体 SKU、开发成熟度和供应链仍需在项目落地阶段核实。

## 7.3 独立 AI Accelerator

Houmo LQ50、Axelera Metis、Hailo-10H、Cambricon MLU 等属于独立 AI accelerator。

这类产品的典型价值是“给已有主机增加 AI 推理能力”。例如 RK3588 已经负责摄像头和系统控制，但 NPU 算力不足，可以通过 M.2 卡把目标检测或大模型卸载出去。

它们的主要比较维度不应只有 TOPS，还要看 onboard memory、PCIe 带宽、功耗、支持模型、编译工具和 ARM Host 兼容性。

## 7.4 Host + Accelerator 已经产品化

Firefly AIBOX PRO 等产品说明 RK3588/RK3576 Host + M.2 AI accelerator 已经成为现成市场路线。

这个事实很重要，因为它证明“Host+Accelerator”不是理论拼装，而可以做成完整 Edge AI Box。但对于无人装备，还需要进一步验证整机重量、散热、Camera 接入和 P99 时延。

换句话说，现成产品证明“架构可实现”，并不自动证明“适合小型无人机”。

## 7.5 工业/机器人整机

Seeed、Advantech 等机器人计算机通常已经集成 GMSL、CAN、宽压输入、M12 接口和工业温度设计。

这些能力对 UGV、USV、AMR 和工业机器人很重要，因为用户购买的不是一颗芯片，而是能直接接传感器和车辆总线、长期运行的计算节点。

但这类产品往往重量达到数百克甚至数千克，因此不能直接用于小型 UAV。对不同无人平台必须重新做 SWaP 匹配。

## 7.6 国产化观察

国产路线目前已经覆盖三种主要形态：

1. RK3588、BM1688、Atlas 等 Integrated SoC/Core；
2. 后摩、寒武纪等独立 AI accelerator；
3. RK Host + 国产 accelerator 的完整异构盒。

这意味着“有没有国产算力芯片”已经不是主要问题。更大的差距在于软件生态和系统级证据，包括 ROS 2、VIO/SLAM、多摄同步、多 workload 并发、P95/P99 和长时间热稳态。

因此后续国产平台验证的重点不应继续停留在收集 TOPS，而应转向系统 Benchmark。

# 第八章 安全可信型无人装备端侧智能计算平台

## 8.1 为什么无人装备需要 Trust Plane

普通服务器通常运行在机房，有受控物理环境和稳定网络；无人装备则可能被部署到无人值守甚至对抗环境。设备有可能失联、被获取、被拆卸，或者长期通过无线链路接受任务和升级。

因此端侧节点除了“算得快”，还要回答一组安全问题：

- 当前接入系统的设备是不是合法设备；
- 启动的软件和固件有没有被替换；
- AI 模型和配置有没有被篡改；
- 私钥和任务密钥是否会因设备被捕获而泄露；
- 远端能不能确认这台设备目前处于可信状态；
- 被判定失陷后能不能撤销它继续加入 Fleet 的权限。

这些问题共同构成 Trust Plane 的设计范围。

## 8.2 Root of Trust：从哪里开始相信系统

RoT（Root of Trust，可信根）是整个信任链最底层、最难被普通软件替换的一部分。它可以来自 BootROM、eFuse、硬件唯一密钥、TPM/TCM 或独立安全芯片。

可信系统的基本逻辑是：先信任不可修改的 BootROM，再由它验证下一阶段 bootloader，bootloader 再验证 kernel 和系统镜像，最终建立一条启动信任链。

如果最底层可信根本身可以被软件修改，那么后续所有“签名验证”都可能被绕过。

## 8.3 Secure Boot 与 Measured Boot

Secure Boot（安全启动）解决的是“未经授权的软件能不能启动”。每一阶段启动代码都验证下一阶段签名，签名不正确就停止启动。

Measured Boot（度量启动）解决的是另一个问题：“远端怎么知道当前到底启动了什么”。它会对 bootloader、kernel、rootfs 等计算 hash，并将结果记录在可信硬件中。

两者可以同时使用：Secure Boot 负责本地阻止非法软件，Measured Boot 为 Remote Attestation 提供证据。

## 8.4 TEE、TPM/TCM 与商密安全芯片

TEE（Trusted Execution Environment，可信执行环境）用于把一部分关键代码和数据放到与普通 Linux 隔离的安全世界。它适合做密钥封装、签名、敏感策略和安全服务，但通常不适合把完整 YOLO、VIO 或 VLM 全部搬进去运行。

TPM/TCM 更擅长平台度量、PCR、sealed key 和 Quote，因此适合做远程证明。

商密安全芯片则更适合保存不可导出私钥，执行 SM2/SM3/SM4 和随机数等密码服务。

这三类技术解决的问题不同。一个有商密芯片的平台不等于已经实现完整可信计算；一个有 TEE 的 SoC 也不等于 GPU/NPU 和全部 DDR 都处于安全执行环境。

## 8.5 Remote Attestation：让远端知道“你现在运行的是什么”

Remote Attestation（远程证明）是安全可信无人平台非常有特色的一项能力。

一个典型流程是：

```text
无人装备 Attester
→ 提交设备身份 + 启动/软件测量值 + nonce
→ Verifier 验证
→ 形成可信判断
→ Ground/Fleet Controller 决定是否允许加入任务网络
```

这里的核心是把“身份”与“状态”绑定起来。仅有证书只能说明“它是谁”，但不能说明这个设备是否已经被刷入恶意系统。

未来可以进一步把 mission key、model key 或 Fleet credential 的释放绑定到 attestation result：只有设备通过可信验证，才获得执行当前任务所需的密钥。

## 8.6 AI Artifact Trust：模型也必须成为可信对象

传统 Secure Boot 主要验证固件和系统，但在 AI 系统中，模型权重、配置、阈值和预后处理代码同样可能影响任务结果。

因此需要建立 AI Artifact Trust（AI 制品可信）：

```text
Model Weight
+ Model Manifest
+ Runtime
+ Config
+ Threshold
+ Pre/Post
+ Planner Parameters
```

这些对象至少应具有签名、hash、版本和授权信息。加载模型前先验证来源和完整性，避免攻击者把正常检测模型替换成经过后门修改的模型。

## 8.7 Physical Capture：设备失陷后的安全

无人机和无人车与机房服务器最大的差异之一，是设备本体可能被对方直接获取。

因此需要考虑：

- 禁用或锁定 debug 接口；
- 系统盘和任务数据加密；
- 私钥不可导出；
- 记录拆卸/tamper 事件；
- 远程吊销设备证书；
- 轮换编队和任务密钥；
- 必要时让设备进入 decommission 状态。

这类“被捕获后的安全”是安全可信无人智算平台能够形成明显行业特色的方向。

## 8.8 三平面总体架构

建议最终产品形成：

```text
                Ground / Fleet Trust Service
          CA / KMS / Verifier / Policy / OTA
                         │
                         ▼
┌───────────────────────────────────────────────┐
│ Secure Trusted Edge Intelligence Node        │
│                                               │
│ Trust Plane                                   │
│ RoT / TEE / TPM-TCM / SE                     │
│ Identity / Key / Measurement / Attestation    │
│ Model Verify / Secure Storage / Crypto        │
│                                               │
│ Compute Plane                                 │
│ CPU / GPU / NPU / ISP / VPU                  │
│ ROS2 / VIO / SLAM / AI / Planner             │
│                                               │
│ Real-Time Plane                               │
│ FCU / MCU / RTOS / Safety Supervisor          │
└───────────────────────────────────────────────┘
```

Compute Plane 解决“算什么”，Real-Time Plane 解决“什么时候必须算完”，Trust Plane 解决“为什么可以相信这些计算和参与计算的实体”。

# 第九章 面向典型任务的配置思路

## 9.1 多摄像头智能分析节点

这类设备主要对应 C1：

```text
W1 + W3 + W5
```

它通常不需要定位和路径规划，因此可重点优化视频和 AI 吞吐。适合固定式多摄监控、工业视觉和视频分析。

平台可以采用 integrated SoC，也可以采用 Host+Accelerator。选型重点是多路视频接入、ISP/VPU、DDR、NPU 并发和网络/存储。

## 9.2 视觉自主伴随计算机

C2 Visual Autonomy 是无人机和移动机器人的关键组合：

```text
W1 + W2 + W3 + W4 + W6 + W9
```

这类平台不能只看 NPU，因为 VIO、地图和规划需要大量 CPU/GPU；同时还必须与 FCU/MCU 形成稳定接口。

更合理的工程结构是：

```text
Companion AI Computer
+
Independent FCU / MCU
```

即高层视觉智能和低层实时控制分离。

## 9.3 多传感器自主平台

当系统再加入 LiDAR、Radar 和复杂预测，就进入 C3。典型是高阶 UGV、USV 和大型机器人。

此时传感器接口、时间同步、地图和内存需求明显增加，更倾向于高性能异构 SoC 或多计算单元架构。

## 9.4 大模型增强平台

C4 在 C1/C2/C3 的基础上增加 VLM/VLA。

它的价值主要体现在任务理解、自然语言交互和开放环境语义能力，而不是取代底层定位和控制。

平台需要重点考虑模型能否装入内存、TTFT、token/s、视觉编码器以及 W7 与实时 workload 的资源隔离。

## 9.5 安全可信无人智算平台

在上述任何基础配置上增加 Trust Plane，就形成安全可信型产品。

它的核心卖点不再是单一 AI 算力，而是“经过验证的智能计算节点”：设备身份可信、启动链可信、模型可信、通信可信，并能够远程证明当前状态。

# 第十章 六摄像头无人平台 Case Study

## 10.1 为什么选择六摄项目作为验证对象

六摄像头无人平台非常适合验证本报告的方法，因为它同时包含多摄数据、AI 感知、定位、规划、实时控制和后续安全可信需求。

项目能力不是一次性到位，而是逐步从“能采图”向“能自主导航”发展，因此可以观察每增加一类 workload 后，系统资源如何变化。

## 10.2 当前已确认输入

当前确认：

| 参数 | 当前状态 |
|---|---|
| N_capture | 6 路 |
| downstream width | 1072 |
| downstream height | 1280 |
| downstream format | NV12 |
| actual FPS | GAP |
| 六路 mode 一致性 | GAP |
| Sensor RAW | GAP |
| multi-camera sync | 已确认需要研究/实现 |

这里的 1072×1280 NV12 是当前 downstream 已观测格式，不代表传感器原始 RAW 格式，不能反推出 MIPI 输入带宽。

## 10.3 已观测图像模式的数据量

对于 NV12，单像素平均约 1.5 Byte。六路 1072×1280 图像在不同 FPS 下，一份 image-plane payload 为：

| FPS | 六路 Pixel Rate | 单份 NV12 Payload |
|---:|---:|---:|
| 10 | 82.33 MP/s | 123.49 MB/s |
| 20 | 164.66 MP/s | 246.99 MB/s |
| 30 | 246.99 MP/s | 370.48 MB/s |
| 60 | 493.98 MP/s | 740.97 MB/s |
| 120 | 987.96 MP/s | 1481.93 MB/s |

例如 30 FPS 时，六路仅一份 NV12 图像就约 370 MB/s。如果 ISP 写一次、AI 再读一次、缩放再读写一次、录像再读一次，DDR 实际工作流量会成倍增加。

因此六摄项目首先要解决的是数据通路，而不是先问 NPU 有多少 TOPS。

## 10.4 能力演进与资源变化

### 阶段 A：采集、同步和录像

主要是 W1。

此时重点不是 AI，而是：

- 六路摄像头能否稳定接入；
- 时间戳是否一致；
- 是否掉帧；
- ISP 是否支持目标模式；
- 编码是否占用额外 CPU。

这是后续所有算法的基础。

### 阶段 B：目标检测与跟踪

增加 W3/W5。

此时需要冻结究竟几路摄像头进入检测，检测频率是多少，以及采用 PER_VIEW 还是 FUSED_MULTI_VIEW。

只有这些参数确定后，才能计算真实 NPU 调用率。

### 阶段 C：深度、障碍与局部避障

增加 Depth、W4 和 W6。

此时系统从“识别”进入“闭环”，必须开始关注 Frame Age 和总反应距离。

### 阶段 D：VIO/SLAM 与自主导航

增加 W2/W4/W6。

VIO 会显著增加 CPU/GPU、时间同步和内存需求，因此这一阶段是判断“一体 SoC 是否仍然足够”的关键。

### 阶段 E：可选 VLM

VLM 作为 W7 增量能力，可以用于场景解释、开放词汇识别和任务理解，但不应直接进入基础避障闭环。

## 10.5 候选架构的理解方式

### RK3588 一体方案

RK3588 同时具有 CPU、GPU、NPU、ISP 和视频能力，因此代表低成本 integrated SoC 路线。

它的价值是数据路径短、产品集成度高；需要验证的关键不是“6 TOPS 小不小”，而是六摄接入、VIO+Detection 并发、DDR 和热稳态。

### Jetson Orin 方案

Jetson Orin 的优势在于 GPU 和软件生态，适合同时承担 VSLAM、Depth、DNN 和复杂 CUDA workload。

需要重点权衡的是功耗、重量、成本和国产化。

### IQ-9075 方案

IQ-9075 面向机器人、多摄像头和异构计算，具有较完整的机器人 SoC 定位。

当前关键 GAP 在于本项目同构多 Camera、VIO 和完整闭环的公开数值证据仍不足。

### RK3588 + Accelerator

这一方案把 RK3588 作为 Host，继续负责 W1/W2/W4/W6，再把 W3 或 W7 卸载到独立 AI 卡。

它可能提升模型容量和吞吐，但同时增加 PCIe、板级、热和总系统功耗。因此是否优于一体 SoC 必须通过相同 workload 的 E2E Benchmark 判断。

## 10.6 六摄项目的安全可信扩展

六摄平台可以从普通视觉计算节点逐步升级为 Trust Platform：

1. 为每台设备建立唯一身份；
2. 启用 Secure Boot；
3. 为模型和关键配置建立签名；
4. 通过商密芯片保护设备私钥；
5. 对 FCU 与 Companion 通信做双向认证；
6. 对 ROS 2 topic/service 做最小权限；
7. 加密任务数据和敏感日志；
8. 引入 Remote Attestation；
9. 建立安全 OTA；
10. 对失陷设备执行证书吊销和任务隔离。

这样项目最终验证的不只是“六路视频能不能跑”，而是“一个无人智能节点能否在计算、实时和安全三个平面上形成完整产品闭环”。

# 第十一章 技术发展趋势

## 11.1 从单传感器感知走向时空多模态融合

早期 AI 系统往往逐帧处理单个摄像头，未来趋势则是同时使用多个 Camera、LiDAR、Radar 和历史帧。

BEV 和 Occupancy 正是这种趋势的代表。它们让系统不再只输出“图像里检测到了几个框”，而是形成统一空间中的环境表示。

这种变化会显著增加 DDR、内存容量和多模型并发压力。

## 11.2 模块化与 End-to-End 长期并存

端到端（End-to-End，E2E）方法尝试用一个大模型直接完成从传感器到轨迹甚至动作的映射。

它的优势是可以减少人工设计模块，但缺点是可解释性、验证和安全边界更复杂。

因此在可预见阶段，更现实的产品形态是“确定性安全骨架 + 学习模型增强”，而不是完全取消传统定位、规划和安全模块。

## 11.3 VLM/VLA 将向端侧渗透，但首先受内存限制

VLM/VLA 可以提高机器人对开放场景和自然语言任务的适应性，因此会逐步进入端侧产品。

但相比传统 YOLO，VLM/VLA 权重和 KV Cache 大得多。未来机器人平台的竞争将越来越看重内存容量、内存带宽和多精度支持，而不只是 INT8 TOPS。

## 11.4 World Model 更可能分层部署

World Model（世界模型）尝试学习环境的动态规律，用于预测未来场景、规划和仿真。

大型世界模型的训练和完整推理可能更多位于服务器或边缘节点，而无人装备本机部署压缩后的预测模型和策略模型。这会进一步推动 Edge-Cloud 分工。

## 11.5 多机器人系统把网络和可信身份变成算力平台问题

当无人平台从单机发展到 Fleet，单机计算节点就成为分布式系统的一部分。

此时“谁可以加入协同”“共享的感知信息是否来自可信设备”与网络带宽同样重要。因此 Trust Plane 和 Fleet Management 很可能成为未来无人算力平台的标准能力。

# 第十二章 对后续产品研发的建议

## 12.1 产品定位：不要做单纯“更大 TOPS 的盒子”

当前市场已经存在大量 Jetson 工业整机、RK AI Box、M.2 accelerator 和机器人计算机。如果仅以算力数字为卖点，新产品很容易与现有厂商正面同质竞争。

公司更有基础形成的差异化是：

> **以无人装备智能计算为载体，把密码能力、设备可信身份、模型可信和全生命周期安全做成平台级能力。**

## 12.2 建议形成三平面产品架构

### Compute Plane

负责：

- Camera / ISP / VPU；
- CPU/GPU/NPU；
- ROS 2；
- VIO/SLAM；
- DNN/VLM；
- Planning。

### Real-Time Plane

负责：

- FCU/MCU；
- 实时控制；
- Safety Supervisor；
- Failsafe。

### Trust Plane

负责：

- RoT；
- SM2/SM3/SM4/TRNG；
- Device Identity；
- Secure/Measured Boot；
- Attestation；
- Secure Storage；
- Model Trust；
- Communication Security；
- OTA；
- Capture Response。

三者之间不是简单堆叠，而应通过统一接口和策略协同。

## 12.3 Trust Service API

建议把 TEE、TPM/TCM、商密安全芯片等底层能力封装为统一 Trust Service：

```text
/device/identity
/crypto/sign
/crypto/encrypt
/key/unseal
/model/verify
/platform/measure
/platform/attest
/update/verify
/security/event
```

这样 ROS、AI Runtime 和任务应用不直接绑定某一颗安全芯片。未来更换 SoC、切换国产器件或形成多个产品档位时，安全能力可以复用。

## 12.4 产品系列建议

### 轻量型无人智能节点

重点面向 UAV、小型机器人。

优先：
- Integrated SoC；
- 多 Camera；
- 低功耗；
- 独立 FCU；
- 基础 Trust Plane。

### 高性能机器人/无人平台节点

面向 UGV、USV 和高级机器人。

重点：
- 大内存；
- GPU/NPU；
- 多传感器；
- 高速网络；
- 完整 Trust Plane；
- 可选 VLM/VLA。

### Host + Accelerator 扩展型

用统一 Host 搭配不同 M.2/PCIe accelerator，形成不同 AI 性能档位。

该路线应明确 Host 是产品的一等组成部分，而不是只销售一张“算力卡”。

## 12.5 Benchmark 体系建议

### Camera/Video Benchmark

测试六路或目标路数同步采集、掉帧、时间戳、ISP、编码和 DDR。

### VIO/SLAM Benchmark

使用 EuRoC、TUM-VI 等公开数据集，同时记录精度、CPU/GPU 占用和延迟。

### DNN Benchmark

固定模型、输入、精度和运行时，比较 latency、FPS、功耗和温度。

### Multi-Workload Benchmark

同时运行：

```text
Camera + VIO + Detection + Depth + Planner
```

重点记录 P50/P95/P99、Frame Age、deadline miss 和系统功耗。

### Host + Accelerator Benchmark

专门测 H2D/D2H、PCIe、copy、pre/post 和端到端延迟。

### Thermal Benchmark

进行 30min、1h、2h 长时间运行，观察温度、频率和是否 throttling。

### Security Benchmark

验证：
- Secure Boot 篡改阻断；
- model tamper；
- attestation；
- key non-exportability；
- rollback；
- unauthorized ROS 2/MAVLink access；
- device revoke。

## 12.6 六摄项目近期最值得冻结的参数

当前优先级最高的不是再找更多芯片，而是冻结：

1. 实际 Camera FPS；
2. 六路 mode；
3. N_detection；
4. N_vio；
5. N_depth；
6. N_record；
7. 飞行速度；
8. usable detection range；
9. vehicle response；
10. 计算节点功耗、尺寸和重量边界。

这些变量一旦明确，就能真正从“调研”进入“平台架构设计”。

# 结论

本次调研最核心的结论不是给出一张端侧芯片 TOPS 排名，而是建立一套面向无人装备的可复用分析方法。

无人平台真正需要的是一个由传感器输入、异构计算、实时控制、软件生态和安全可信共同组成的系统。不同任务会产生不同 workload，workload 又会决定 CPU、GPU、NPU、内存、接口、功耗和时延需求。只有完成这一层层映射之后，产品选型才有工程意义。

从当前产业情况看，高集成 SoC、GPU 机器人平台、AI accelerator 和 Host+Accelerator 都已经形成成熟路线。继续单纯追求“更大 TOPS”的产品很难形成长期壁垒。

结合公司的技术基础，更值得推进的方向是：

> **安全可信无人装备端侧智能计算平台：以异构 AI 计算为基础，以实时控制分区保证闭环，以商密和可信根建立设备身份和平台信任，并把模型、通信、升级和失陷处置纳入统一生命周期。**

六摄像头无人平台可以作为这一方向的首个系统验证载体。通过逐步加入多摄采集、VIO、DNN、Depth、Planner、FCU 闭环和 Trust Plane，可以形成一套可复现 Benchmark，并最终反向确定真正有依据的产品规格。
