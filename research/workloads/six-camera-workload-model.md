# 六摄像头无人平台工作负载模型

- 状态：v0.1
- 日期：2026-09-29
- 目的：把“六路摄像头 + 智能任务”转换为可计算、可测试的系统资源需求
- 原则：未知输入保持“待确认”，不以产品 TOPS 反推需求

## 1. 研究问题

六摄像头无人平台要从“能采图”逐步升级到检测、融合、避障、VIO/SLAM、自主导航甚至 VLM。每增加一类任务，都需要回答：

1. 输入数据量是多少？
2. 数据在 ISP、CPU、GPU/NPU、内存之间如何流动？
3. 模型和传统算法的计算量是多少？
4. 哪些任务同时运行？
5. 最大允许端到端延迟是多少？
6. 峰值性能、持续性能、功耗和温度分别是多少？
7. 哪个资源先成为瓶颈？

## 3. 数据入口模型

### 3.1 传感器有效像素数据率

对单路未压缩图像：

```text
B_camera = W × H × F × bpp
```

六路总有效数据率：

```text
B_total = N × W × H × F × bpp
```

其中：

- W、H：有效像素尺寸；
- F：帧率；
- bpp：每像素有效位数；
- B 的单位为 bit/s。

### 3.2 链路带宽不能只按有效像素计算

实际 MIPI/SerDes 链路还可能包含：

- 行/帧消隐
- 协议包头
- ECC/CRC
- 虚拟通道
- 时钟/编码开销
- 传感器特定 timing

因此应使用：

```text
B_link = B_total × K_link
```

其中 `K_link > 1`，具体值必须依据实际 Sensor timing、MIPI lane 配置或 SerDes 配置计算，禁止统一拍脑袋给一个固定系数。

## 4. 内存带宽模型

摄像头数据进入 SoC 后，通常不是“写一次内存就结束”。

典型过程可能包括：

```text
Sensor
  ↓
ISP写入
  ↓
预处理读取/写回
  ↓
AI输入转换
  ↓
推理
  ↓
后处理
  ↓
拼接/融合/编码
```

粗略模型：

```text
BW_memory ≈ Σ(FrameBytes_i × FPS_i × Passes_i)
```

其中：

- `FrameBytes = W × H × bytes_per_pixel`
- `Passes` 表示该帧在主存中的完整读写次数

需要单独记录：

- ISP 写流量
- CPU/GPU 读取
- NPU DMA
- 格式转换
- 拼接/融合
- 编码器输入
- 显示/存储

### 工程判断

多摄像头系统中，**内存带宽可能在 NPU TOPS 用满之前先成为瓶颈**。

因此后续 Benchmark 必须同时采集：

- AI 单元利用率
- DDR 带宽/控制器占用
- CPU/GPU占用
- 内存复制量

零拷贝、DMA-BUF、共享 buffer 等数据通路优化需要作为平台能力的一部分评估。

## 5. 视频处理负载

视频编解码能力应至少用两种口径描述。

### 5.1 像素吞吐

```text
PixelRate = N × W × H × F
```

单位：pixel/s。

这是比较多路 1080p/4K 视频处理能力的基础量。

### 5.2 编码码率

编码后的 Mbps 取决于：

- H.264/H.265/AV1 等编码格式
- 场景复杂度
- GOP
- QP/码控
- 是否低延迟
- 画质要求

因此不能用“原始图像数据率”直接代替视频码率，也不能只看厂商宣称的单路最大分辨率。

平台验证应使用目标场景的**六路并发编码**。

## 6. AI 推理负载模型

对第 i 个模型：

```text
Compute_i = OpsPerInference_i × InferenceRate_i × StreamCount_i
```

系统总理论负载：

```text
Compute_total = Σ Compute_i
```

但该值只用于建立数量级，不直接等于平台所需 TOPS。

原因包括：

1. 厂商对 MAC/FLOP/OPS 的计数口径可能不同；
2. 算子并非全部运行在 NPU；
3. 前处理、后处理和 NMS 等可能落在 CPU/GPU；
4. 内存访问可能限制实际吞吐；
5. 多模型并发时调度开销增加；
6. 实际量化精度可能不同；
7. 编译器/SDK 算子覆盖率不同。

因此必须同时记录：

- 单路模型 FPS
- 单次 latency
- 六路并发 FPS
- P50/P95/P99 latency
- NPU/GPU利用率
- CPU占用
- DDR带宽
- 功耗
- 温度

## 7. 多任务并发模型

真实系统更接近：

```text
T0: 6×Camera采集
T1: ISP / 图像预处理
T2: 目标检测
T3: 多目标跟踪
T4: 深度/障碍物
T5: VIO/SLAM
T6: 地图/规划
T7: 视频编码/记录
T8: 网络传输
T9: VLM（可选）
```

需要建立任务矩阵：

| 任务 | CPU | GPU | NPU | ISP/VPU | DDR | 实时级别 | 是否常驻 |
|---|---|---|---|---|---|---|---|
| 六路采集 | 待测 | - | - | 高 | 高 | 高 | 是 |
| 图像预处理 | 待测 | 待测 | -/可选 | 中 | 高 | 高 | 是 |
| 检测 | 中 | 可选 | 高 | - | 高 | 高 | 是 |
| 跟踪 | 中-高 | 可选 | 可选 | - | 中 | 高 | 是 |
| 深度估计 | 待测 | 高/可选 | 高/可选 | - | 高 | 高 | 按需求 |
| VIO/SLAM | 高 | 高/可选 | 低/可选 | - | 高 | 很高 | 按需求 |
| 路径规划 | 高 | 可选 | 低 | - | 中 | 很高 | 按需求 |
| 视频编码 | 低 | 低 | - | 高 | 高 | 中 | 按需求 |
| VLM | 高 | 高/NPU | 高/可选 | - | 很高 | 中 | 可选 |

> 表中“高/中/低”是待验证的关注度，不是测试结论。

## 8. 端到端延迟模型

对于避障或实时感知，不能只看模型推理 latency。

完整延迟：

```text
L_total =
L_exposure
+ L_sensor
+ L_transport
+ L_ISP
+ L_buffer
+ L_preprocess
+ L_inference
+ L_postprocess
+ L_fusion
+ L_planning
+ L_control_interface
```

后续应测量实际时间戳，而不是只将各模块宣传值相加。

### 关键风险

如果各模块异步排队，即使单模型只需要几毫秒，整体仍可能出现几十到数百毫秒延迟。

因此必须记录：

- 平均延迟
- P95/P99 延迟
- 最坏情况
- 丢帧
- 队列深度
- Frame Age

---

## 9. 同步负载与误差

六摄像头拼接、多目深度和 VIO 都对时间同步敏感。

需要分别记录：

- 触发同步方式
- Sensor 时间戳来源
- IMU 与 Camera 的时钟关系
- 六路 Frame Start 偏差
- 驱动层到用户态的时间戳传播
- 多路帧配对策略

同步问题不是“算力不足”，但会直接决定算法效果，因此必须进入平台能力模型。

---

## 10. 内存容量模型

系统所需内存不能只按模型权重估计。

```text
Memory_total ≈
OS/Runtime
+ ModelWeights
+ Activations
+ CameraBuffers
+ ISP/VPU Buffers
+ SLAM Map
+ ROS2 Queues
+ VLM KV Cache
+ Application Cache
+ Safety Margin
```

### 对 VLM/LLM

还需要单独记录：

- 参数量
- 权重量化精度
- 最大上下文
- KV Cache
- 多模态 encoder 占用
- 并发请求

因此大模型/VLM/VLA 工作负载的平台比较中，内存容量和带宽往往比 INT8 TOPS 更有解释力。

## 11. 功耗与热设计

应以**持续工作负载**而不是短时间峰值性能评估。

```text
P_system =
P_compute
+ P_camera
+ P_storage
+ P_network
+ P_peripheral
+ P_conversion_loss
```

需要测试：

- 空闲功耗
- 六路采集功耗
- 六路采集 + AI
- 定位/导航满负载
- 持续 30/60/120 min 温度
- 是否发生降频
- 降频后的 FPS/延迟变化

对于无人机，还应转换为：

- Wh/mission
- 对续航时间的影响
- 散热器/风扇重量

## 12. Benchmark 阶段

### B0：平台基础能力

- CPU
- GPU
- NPU
- DDR带宽
- 存储
- 网络
- 视频编解码

### B1：六路视频

- 1/2/4/6路采集
- 六路同步
- 六路编码
- 丢帧率
- DDR占用
- 持续功耗

### B2：实时感知

- 1/2/4/6路检测
- 检测 + 跟踪
- 检测 + 深度
- 多模型并发

### B3：定位导航

- VIO/SLAM 单独运行
- VIO/SLAM + 6路采集
- VIO/SLAM + 检测
- 地图 + 规划 + 避障

### B4：高级认知

如存在明确任务价值，再测试：

- VLM 单次图片理解
- 视频/多帧输入
- TTFT
- Token/s
- 与实时感知、VIO/SLAM、规划任务并发时的性能退化

## 13. 平台适配判定

平台不是“能跑起来”就算适配。

建议至少分成：

### 可运行

功能能够执行。

### 可实时

满足目标帧率与延迟。

### 可并发

关键任务同时运行仍满足实时要求。

### 可持续

长时间运行无明显热降频、内存泄漏或稳定性问题。

### 可产品化

进一步满足：

- SWaP
- 供货
- 成本
- 软件维护
- 模型部署
- 接口
- EMC/环境适应性等要求

---

## 14. 下一步需要获取的数据

第一优先级不是找更多芯片，而是冻结或测量以下输入：

1. 六路相机分辨率；
2. 帧率；
3. 像素格式/传感器输出；
4. 是否需要六路录像；
5. 同步要求；
6. 第一版检测模型；
7. 第一版避障算法路线；
8. 目标端到端延迟；
9. 目标功耗；
10. 现有平台实测 CPU/DDR/NPU 占用。

得到这些数据后，才进入第一轮定量算力推导。
